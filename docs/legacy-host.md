# Legacy Host entry on independent Runtime

`evopilot_v01_guide` remains an offline, read-only tool. The `v01` namespace is
historical; it does not identify the current Runtime version. Starting the
ordinary compatibility entry without a connection exposes only the guide. A missing or
unavailable connection cannot prevent a guide call. Service calls still require
the exact protected connection; the bridge never starts a daemon, creates a
Workspace, opens a Runtime database or grants permissions.

An explicitly configured local Workspace operator can additionally expose the
six maintenance tools described below while HTTP is offline. This uses the
installation bootstrap, not an HTTP operation or implicit permission from loading
the plugin.

The guide preserves the original named scenarios and V02–V08 identifiers. V02
use cases and all original test paths describe historical provenance, not current
acceptance evidence. Guide text is not capability discovery: inspect advertised
tools and the selected service's current scoped capabilities before executing a
step. A missing provider, helper or permission remains a prerequisite failure.
Do not emulate missing product features with untracked temporary scripts.

Resolve `installedReferences` against this Runtime package root. Resolve an
`ownerReferences` entry against the explicitly registered, verified published
Ontology or Harness **0.8.3** package root. Do not resolve through an EvoPilot
parent installation, plugin cache, current directory or sibling source checkout.
Owner schemas, standards and native lifecycle remain authoritative.

## Definition and operation boundaries

Legacy project preparation, private Goal/Target/Loop records and content grades
never activate a new Project Lifecycle. The v0.9 lifecycle independently requires
all mandatory Base configuration, verified GitHub/GitLab bindings and same-entry
save-and-activate. Runtime's two Dashboard pages are the lifecycle editor and a
separate read-only instance monitor. Owner asset authoring stays in the configured
published owner entry; the Runtime HTTP service does not gain that authority.

The stdio bridge forwards legacy Runtime requests to the same independent HTTP
service. An explicit owner Host registration delegates only its allowed calls
to published owner APIs. Activation is session intent, not execution or release
permission. Deactivation affects that session, not a peer chat or the service.
Workspace maintenance must preserve the new service state, private project,
owner state, claims and evidence under one writer. A live capacity scan or the
Runtime-only migration backup is not a full consistent Workspace backup.

The independent operator helpers in `src/installation/workspace/` provide
managed schema-9 snapshots and resumable backups. The exact selected private
project, owner workspace and service installation are separate roots. The
operator must stop the selected Runtime and any separate online worker first;
the helpers retain the shared Host lease and both Runtime writer leases during
inspection and copying. They do not stop, restart or reconcile business work.
An installed helper can include its own exact `serviceRoot/package` distribution
when the protected specification matches; this does not permit a source checkout
or an arbitrary ancestor directory to become a maintenance root.

All database tables and selected payload files are preserved. SQLite validation
uses disposable copies, and the new service's receipt/audit/event ledger is
checked there. Business WAL/SHM/journal files block capture. Only temporary journals created by the held, empty writer and installer
lock files are excluded, with their
exact paths recorded in `transientExclusions`; the empty lock files are retained.
An unchanged workspace produces the same snapshot digest across acquisitions.

The backup includes service specification references and explicitly selected
additional reference files. External source trees, owner distributions,
toolchain caches and relocation signing keys are not recursively imported by
following JSON paths. Required lineage key identifiers remain in the manifest;
same-host key availability is still a recovery prerequisite. Coverage is stated
as `SELECTED_ROOTS_AND_REFERENCE_FILES`, not a claim to recreate the complete
external environment. Keep backup roots private and their expected digest in
the separate retained maintenance record. Verification checks that external
digest, every copied file and mode, internal relative links and reference bytes.
An interrupted copy resumes only the same request and verified prefix; source
drift or foreign partial content is rejected without overwriting it.

The operator restore helper accepts the known backup and its external digest,
and restores only its original missing/empty roots. It requires the retained
backup anchor and lineage keys, and refuses a loaded Runtime or online worker
job even if that job currently has no running process. Both writer locks protect
the destination while it is copied. Recover an unavailable installation from a
separate verified Runtime package; do not remove the executing rescue package.
Missing selected external configuration files may be restored; existing files
must match exactly and are never replaced. An interrupted copy or exclusive
reference publish can resume only the same retained request. Every database,
payload and selected reference is checked again before recording completion.

Restore preserves pending work and returns `serviceStarted: false` and
`businessWorkDispatched: false`. Startup remains a separate explicit operator
step. A repeated completed request returns its historical restore receipt and
cannot overwrite subsequent work; it does not certify the current environment.
The durable location operator and selected Host maintenance aliases are described
below; final migration acceptance remains separate. Neither this documentation nor source tests mark
the complete legacy maintenance path or final product acceptance passed.

Physical preservation checks retain each published owner's signed audit format:
Ontology's mirrored native receipt rows are covered by its separate native audit
digest, while Harness also binds that native audit alongside its legacy ledger.
Runtime's original ledger format stays unchanged. The operator checks these on
private copies, including signatures, retained keys and the complete table
inventory; it does not reinterpret owner business outcomes or rewrite records.

The Runtime relocation core now preserves adopted schema-9 state using the
existing signed same-host lineage. All business tables, their schema and the
original adoption seal are included in the snapshot. A managed move returns a
new location binding without rewriting that seal or any original claim/receipt.
Plain directory copies, stale bindings, changed destination records and missing
lineage keys are rejected. The durable operator below composes service configuration cutover. Its selected Host
migration entry uses the same core; this core never starts a service
or redispatches work.

The operator configuration assembler can prepare the new service, connection,
scoped provider/owner Host registrations, plugin and launchd material after the
exact copied workspace has acquired its signed location binding. Assembly is
read-only: the caller must hold maintenance leases, retain a durable request and
apply the reviewed bytes before explicit startup. It preserves service identity,
ports, principals, permission selections, expiry, credentials, resource
definitions, immutable adoption and original installation history. Only declared
operational paths move; arbitrary strings inside definitions and old claims do
not. Published owner packages, native toolchain dependencies and other external
references remain required at their retained locations unless explicitly copied.

The prepared material contains hashes and configuration bytes with credential
references. It contains no client or platform token values and cannot renew
authority or register Codex. Changed copied credentials, service state, package
files or original Host permissions are rejected. Prepared bytes do not make old
execution claims current or authorize restarting them. The durable operator below applies these bytes under its retained journal and
leases. Selected Host maintenance aliases use this retained operator flow.

### Durable stopped-workspace relocation / 可恢复的工作区搬迁

externally anchored same-host backup, exact three-root copying, public published
Ontology/Harness location attestations, managed Runtime lineage and the prepared
service/Host configuration. Supply the exact source selection, three new roots,
backup reference/digest, published owner package paths, original Host selection
and a stable request ID. Stop both Runtime user jobs and online workers first.
No HTTP request or project YAML can select this operator operation.

Both workspace coordination leases, managed/service writer locks and existing
installer locks remain held during the operation. A nonterminal lifecycle
stage or an owner `RECONCILE_OR_CANCEL` item blocks relocation. The source
snapshot must remain unchanged, every non-location database table/schema is
compared, and credentials, immutable adoption, original installation plans and
source directories are retained. Only declared operational configuration paths
change. The original backup and its anchor are retained at their original
locations; the result records that reference, rather than inventing a new backup.

The protected request journal preserves copied/attested/configuration progress.
Retry the **same request**, after inspecting its failure. Exact partial copies
and prepared configuration bytes may resume; different input, foreign files,
changed domain tables or new writes are refused. A completed retry returns the
original historical receipt without replacing newer target data. A VERIFIED
result starts no service, registers no Codex plugin and dispatches no business
request. Explicit attachment/start remains a separate operator step. Source
regressions are not final E15 or the 664-case acceptance.

### Stopped Workspace preparation core / 停机工作区准备核心

`installation/workspace/bootstrap.ts` prepares an explicitly selected editable
project and owner workspace for independent Runtime installation. The selection
pins the project/state/service roots, workspace ID, fixed published owner
packages, `initialize` or `attach`, and a retained request ID. Defaults and Host
registration belong to the later entry composition; this core never chooses
daily paths, starts a service or restores the retired parent daemon.

Initialization requires empty or absent project/state roots. Attachment requires
the existing canonical workspace identity and preserves existing project files
and template versions; it can create a missing editable project. Both flows use
the six pinned original template files and initialize only through Runtime and
the verified published Ontology/Harness **0.8.3** APIs. An already managed
workspace is inspected under its exact current service binding and writer
capability, without opening it through an old Runtime writer. A service bound
to another workspace cannot be switched by this operation.

The selected Runtime and online worker must be stopped. Original connection
claims, independent writer/installer locks, unsafe locations and conflicting
requests block preparation. Installation and Workspace coordination leases
protect the retained intent; owner initialization is idempotent, project file
publication is exclusive, and an interrupted request must resume under the
same selection. Replacing an unfinished request is refused. Original business
requests and receipts are not dispatched, canceled or rewritten.

The result is **PREPARED**. `serviceBindingRequired` distinguishes a workspace
awaiting independent installation from an already managed same-service
attachment; neither means that a service or session was activated. A completed
retry returns historical evidence with `currentEnvironmentVerified: false`,
preserving subsequent data. The original installation/adoption records remain
unchanged. The protected first-use operator below composes this core with
`workspace_initialize` / `workspace_attach`, binding and selected service state.
An accurate final candidate and actual Codex journey remain required for acceptance.

准备核心明确选择项目、状态和服务目录，不自动写入日常目录。初始化要求空目录；
接入保留已有工作区身份、业务记录、项目内容和模板版本，也可补建缺失的私有项目。
已受独立服务管理的工作区只能沿用其当前绑定，不能切换至其他服务或通过旧 Runtime
写入。运行中的服务、在线 worker、写锁或未完成的不同请求都会阻止继续。

返回“已准备”不等于服务已启动、插件已安装或会话已激活。中断后沿用原请求；完成后
重复读取返回历史证据，不覆盖新数据，也不证明当前环境已重验。Host 初始化／接入
入口现由下述受保护的首次接入操作组合；开发验证不能代替正式候选的完整接入 E2E。

### Binding prepared state to a stopped installation / 准备后的安装绑定

`installation/workspace/binding.ts` consumes the exact retained setup result,
original installation/connection/specification digests and an independently
verified original Runtime backup. It binds that prepared Workspace to the same
stopped independent service. A different existing binding cannot be replaced.
Owner Host permissions and local maintenance operations are explicit protected
selections; neither setup nor binding grants an asset or business decision.

The operator holds the installation and service writer locks and the shared
Workspace lease. It verifies service state on a temporary copy, retaining the
original database bytes, service ID, credentials, connection and installation
plan. Runtime adoption preserves original business records; owner databases are
not rewritten. Installed package verification uses the retained distribution
manifest and installed bytes, without requiring the original download directory.

The request retains its original backup, adoption, configuration baseline and
failures. A partial configuration switch resumes only the same request and exact
old/new bytes; foreign edits are not overwritten. The service specification is
published last, after plugin routing and the launchd configuration. Recovery of
an already committed adoption uses its original seal, including after process
death. Completed replay is historical and explicitly does not certify current
environment validity.

The result is **BOUND**, with `serviceStarted`, `hostRegistered`,
`sessionActivated` and `businessWorkDispatched` all false. Startup must explicitly
select the resulting current specification. The original installer plan remains
immutable and cannot be replayed as a replacement for the changed configuration.
The protected initialize/attach operator composes this core. The core alone
does not establish onboarding or final candidate acceptance.

绑定使用已保留的准备结果、准确安装身份和已核验备份；原安装计划、服务身份、凭据、
连接及业务记录保持不变。服务数据库在临时副本中核验，原库字节不会因核验而改变。
中断后沿原请求恢复，配置仅接受准确的原值或预期新值，不覆盖其他修改；原失败保留。
返回 `BOUND` 不代表启动服务、启用会话或执行业务。完整插件初始化／接入流程通过
下述操作组合；旧安装计划不能冒充变更后的当前启动配置。

### Protected first-use plugin / 插件首次接入

An unbound installation may explicitly select `workspaceSetup` in its immutable

fields. Neither operation can switch that selection or accept arbitrary paths.

An explicit call stops only the selected independent service, prepares the
Workspace, captures an anchored original Runtime backup and binds the same
service identity. It then applies the selected running/stopped state. The
Runtime-only adoption backup protects the records this operation changes; it
does not claim to be a whole Workspace backup. Interrupted copies reconcile only
the retained source inventory and exact destination prefix. Failures remain as
separate records after recovery; another request cannot replace unfinished work.

Within the same Host process, setup invalidates cached connection/owner routes,
deactivates the compatibility session and sends tool-list-change notification.
Tool calls are serialized across this configuration change. After a running
result the Host can rediscover tools, explicitly activate and use its selected
owner entries without reopening the plugin. HTTP endpoint, credentials and
service ID stay unchanged. A stopped selection needs explicit operator startup.
Completed replay returns its historical receipt without restarting a service.

Binding does not activate a Project Lifecycle, approve assets, start a business
Run or provide release authority. Isolated SDK/launchd/public-owner development
journeys verify this implementation; exact-candidate actual Codex acceptance is
still a separate requirement.

首次接入使用安装时明确配置的项目目录、状态目录、owner 权限、有效期和结束后的服务
状态。加载插件只提供检查入口；用户调用初始化或接入后，才执行停机、准备、备份、
绑定及选定的服务状态。原安装计划与凭据不变。中断沿原请求恢复，失败记录独立保留。
同一会话可刷新工具后显式激活并继续使用，无需安装第二个插件。工作区接入成功不代表
生命周期已启用、业务已执行或软件已获准发布。

## Retained native dependency preparation

An installed local operator grant can explicitly select `toolchain_inspect` and
`toolchain_prepare`. Existing grants do not acquire these calls implicitly.
Inspection verifies the bundled lock and current selected Workspace cache without
creating files or downloading. A historical successful receipt alone does not
establish current readiness; changed dependency bytes fail integrity checks.

Preparation accepts only a stable request ID. Under the shared Workspace lease it
stops the exact independent Runtime, verifies that other workers are stopped and
holds the original writer exclusion while preparing the bundled dependencies.
It returns admission before downloads finish and deactivates the compatibility
session. The caller cannot select a URL, executable, cache location or new lock.
Inspect with backoff. A repeated ID returns its retained result; RUNNING or UNKNOWN
blocks replacement requests. A failed original remains failed even if a later
explicit preparation succeeds. Host loss preserves UNKNOWN rather than silently
repeating the download. The original v1 journal format remains readable.

Dependency readiness, installed owner bindings and service readiness are separate.
Preparation leaves the independent service stopped; explicit operator startup
uses its current verified specification before session activation. It does not
change owner/toolchain registrations, dispatch a Run or grant acceptance. Final
candidate Codex onboarding must verify the complete preparation, binding and
startup sequence; isolated SDK tests do not substitute for that journey.

本机维护权限可明确开放原有的工具链检查、准备入口；旧权限不会自动增加新调用。
检查不下载，准备只使用固定依赖清单，并在停机及工作区互斥保护下执行。准备调用
先返回原请求状态；进程退出后的 UNKNOWN 不能当作重试许可。失败回执不会被后续
成功覆盖。依赖就绪不等于服务已启动或 owner 已绑定，后续需要按准确配置显式启动。

## Control the current installed service

After Workspace binding or relocation, use the installed operator's current
selection rather than replaying the original installation plan. The original
plan, adoption receipt and distribution manifest remain unchanged. Selection is
a passive identity snapshot, not permission to execute business work or publish.

```sh
umask 077
evopilot-runtime-install service select --root /absolute/current-service > /absolute/current-service-selection.json
evopilot-runtime-install service inspect --selection-ref /absolute/current-service-selection.json
evopilot-runtime-install service start --selection-ref /absolute/current-service-selection.json
evopilot-runtime-install service stop --selection-ref /absolute/current-service-selection.json
```

Each operation rechecks the selected original plan, complete installed package,
manifest, current configuration, credentials and connection identity. Start also
checks the stopped original ledger and signed managed binding before launching
the exact service. Replaced data, a competing writer or changed configuration
fails closed. Selecting a new snapshot does not repair or approve the change.
Read the retained failure and review the intended configuration first.

The commands do not re-download, restage, register a Host, rewrite an old plan,
start an online worker or dispatch a business Run. Startup and stop are explicit
and retain their own local audit; inspection never starts a service. A relocated
installation can verify its retained package after the old service root and
temporary downloads have been removed. Separately selected external configuration
and dependency locations must still exist when the current service uses them.

工作区绑定或迁移之后，使用上述当前服务入口。`select` 只输出准确安装身份；配置
变化会使旧选择失效，不会自动覆盖原安装计划。`start`、`stop` 分别显式启停选中的
服务，保留本机操作记录；不会派发业务任务、启动在线 worker 或重新安装 Codex 插件。

## Apply prepared native dependency bindings

After fixed dependency preparation, use the installed local operator to select
and apply the exact current material while the Runtime and online worker are
stopped. The selector verifies the installed distribution, current grants and
every locked dependency; a caller-supplied descriptor is not sufficient.

```sh
umask 077
evopilot-runtime-install toolchain select --root /absolute/current-service > /absolute/toolchain-material.json
evopilot-runtime-install toolchain inspect --material-ref /absolute/toolchain-material.json
evopilot-runtime-install toolchain apply --material-ref /absolute/toolchain-material.json
```

Application retains the material and original configuration under the selected
installation, holds Workspace/installer/writer exclusion, and publishes only
the selected owner/provider/integration/plugin/service configuration. It
preserves scope, expiry, credentials, original installation plans, dependency
preparation receipts and business records. A completed first-use wrapper becomes
the bound maintenance entry without changing its permitted calls.

After interruption, inspect and resume the same material. Only exact original
or intended destination bytes are accepted; other changes are rejected and
retained as a separate failure. A successful replay returns the historical
receipt with `currentEnvironmentVerified: false`; it does not reapply the
configuration or restart a running service.

An `APPLIED` result leaves the service stopped. Select its new current service
configuration, explicitly start it, reconnect the plugin and activate the
session before using the permitted native validation tools. Dependency binding
does not approve assets, dispatch business work or establish product acceptance.

依赖准备完成后，使用以上本机安装器命令核对并应用准确绑定。操作要求对应服务和
在线 worker 已停止；原权限、有效期、凭据、安装计划及历史回执保持不变。中断后检查
并恢复同一份材料，其他配置修改会被拒绝。完成后的重复调用只返回历史回执，不启动
服务。随后选择新的当前服务配置、显式启动、重连插件并激活，再执行已授权的原生验证。
